# Contributing to BeeWave

Thank you for your interest in contributing to BeeWave! We welcome bug fixes, documentation improvements, feature enhancements, and community feedback.

Please review this guide before submitting pull requests or proposing major architectural modifications.

---

## Code of Conduct

All contributors and participants agree to abide by our [Code of Conduct](CODE_OF_CONDUCT.md).

---

## Architectural Invariants

Every contribution must maintain BeeWave's fundamental design rules:

1. **Strictly Receive-Only**: BeeWave never transmits 802.11 management, control, or data frames. We do not accept PRs introducing active injection, jamming, or deauthentication capabilities.
2. **Hexagonal Dependency Direction**: `adapters -> core -> protocol`.
   - `crates/protocol`: Shared wire format (`postcard`), `no_std`, zero dependencies.
   - `crates/core`: Pure domain logic, state machines, and ports. Strictly `#![no_std]` and zero dynamic heap allocations (`heapless` only). No `esp-idf` imports.
   - `firmware/`: ESP-IDF hardware adapters and composition root.
   - `web/`: Vite + TypeScript PWA. Slices depend only on `shared/`.
3. **Wire Format Synchronization**: Modifying wire messages requires touching:
   `crates/protocol` &rarr; `make vectors` &rarr; `web/src/shared/protocol/`.
4. **Web Tooling**: `pnpm` only (pinned in `packageManager`). Never use `npm` or `yarn`.

## Development Setup

The project uses a hermetic Nix environment that provides Rust, Node.js, pnpm, Espup, and build utilities:

```bash
# Clone the repository
git clone https://github.com/ananto30/beewave.git
cd beewave

# Enter the Nix development shell
nix develop
# or with direnv:
direnv allow
```

### Checking Your Environment
Run `make doctor` to verify required tools and serial port access:
```bash
make doctor
```

---

## Testing & Verification

Before submitting any code change, ensure the full local verification gate passes:

```bash
# Run host test suite (Rust unit tests + Vitest)
make test

# Full CI gate (format check, host tests, no_std check, web build, OpenSpec validation)
make check
```

## Commit Guidelines

We enforce clean, structured git hygiene (see `.agents/shared/rules/git.md`):

1. **Conventional Commits**: Format your commit messages as `type(scope): imperative summary`.
   - Types: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`.
   - Example: `feat(core): add RSSI threshold deduplication in scan tracker`
2. **One Logical Part Per Commit**: Keep protocol, core, firmware, web, docs, and spec changes separated into logical commits.
3. **No AI Attribution**: Do not include `Co-Authored-By:` lines attributing AI assistants, "Generated by" footers, or bot emojis.
4. **Author Identity**: Commit with your own personal git name and email.

---

## Submitting Pull Requests

1. Fork the repository and create a branch from `main`:
   ```bash
   git checkout -b feat/your-feature-name
   ```
2. Implement your changes following our [file structure standards](.agents/shared/rules/file-structure.md) (one concern per file, types in `types.rs`/`types.ts`, tests in sibling `tests.rs` or `test/`).
3. Verify that `make check` passes cleanly.
4. Push your branch to GitHub and open a Pull Request using our [PR Template](.github/PULL_REQUEST_TEMPLATE.md).
